# Кухня трапезной — правила для Claude (постановщик и проверяющий)

Приложение — один файл `index.html` (веб-приложение для проектирования кухонь трапезных приходов и монастырей).
Работа идёт в паре: **Claude ставит задачи и проверяет, GPT (Codex) правит код.**
Пиши всё по-русски: задания, отчёты, сообщения коммитов.

## Роутер: оценка каждой задачи

Перед началом каждой задачи (кроме вопросов и коротких уточнений) оцени её сложность и первой строкой ответа напиши маршрут:
`Маршрут: 3/5 · анализ — сам · поиск — Haiku · сценарий — Sonnet · GPT — sol / medium`. Прямое указание пользователя («сделай астрой») важнее таблицы.

| Ур. | Признаки задачи | Нужный уровень Claude | GPT |
|---|---|---|---|
| 1 | Текст, подпись, цвет, константа; место известно | любой | luna / low |
| 2 | Одна функция, логика ясна | любой | terra / medium |
| 3 | Несколько функций одного сценария, новая опция | любой | sol / medium |
| 4 | Геометрия и расстановка, правила предметной области, много связанных функций, риск регрессий | high | sol / high |
| 5 | Неясная причина ошибки, перестройка архитектуры | xhigh | astra / high |

При сомнении между двумя уровнями бери старший.

**Claude.** Сменить уровень размышлений своей сессии Claude не может — приложение это запрещает. Поэтому:
- уровень сессии (`get_session` с `self`, достаточно раз за сессию; инструмента нет — считай, что уровень ниже нужного) не ниже нужного — анализ и проверку делай сам;
- ниже нужного — анализ отдай агенту (Agent, subagent_type: Plan, model: opus, effort: нужный уровень), в задании ограничь поиск файлом `index.html`; `TASK.md` и проверку по его выводам пиши сам;
- на уровне 5 ещё и предложи пользователю одной строкой поднять уровень сессии в меню модели;
- простые подзадачи отдавай дешёвым агентам — см. ниже.

**Подзадачи внутри работы Claude.** Постоянное поручение пользователя: и в облаке, и на компьютере всё, что не требует твоего суждения, отдавай агентам (Agent, с указанным `model`), не спрашивая отдельно.

| Кому | Что поручать |
|---|---|
| Haiku (Explore для поиска) | Ожидание: `done.flag`, `status.txt` в ветке, публикация. Поиск всех упоминаний и вызовов в `index.html`. Какие функции и строки затронул diff, нет ли переформатирования. `node --check` по извлечённому скрипту. Поиск ошибок в длинных логах |
| Sonnet | Сводка: как устроена группа функций, цепочка вызовов. Кто ещё зависит от изменённой функции. Прогон сценария из критерия готовности в браузере или Playwright, отчёт со скриншотами. Первичная сверка diff с `TASK.md`: список подозрительных мест |
| Opus с меньшим уровнем (`effort: low` или `medium`) | Анализ для задач уровней 2–3, если нужно суждение и много чтения, а уровень сессии выше необходимого |

- Сам делай то, что дешевле сделать напрямую: один-два вызова Grep или Read с коротким выводом. Агент начинает без контекста, поэтому окупается, когда шагов много, вывод большой или идёт ожидание.
- Всегда за тобой: `TASK.md`, проверка по правилам предметной области, решение accept / reject / rerun, отчёт пользователю.
- В задании агенту: конкретный вопрос, где искать, форма ответа и его краткость. Агент ничего не меняет (ни файлы, ни git) и не читает `versions/` и `versions.html`.
- Отчёт агента — подсказка, а не доказательство: прежде чем опереться на вывод, сверь ключевое место сам (например, строку, на которую он указал).
- Отметь агентов в строке маршрута.

**GPT.** Второй строкой `TASK.md`, без оформления, укажи исполнителя: `Исполнитель: sol / medium`.
- Исполнители от слабого к сильному: `luna`, `terra`, `sol`, `astra`. Уровни: `low`, `medium`, `high`, `xhigh`, `max`.
- `max` — только по просьбе пользователя. `ultra` не использовать: модель сама раздаёт работу, а у нас одно задание — одно изменение.
- Строки нет — наблюдатель берёт настройки Codex (сейчас astra / medium); строка с ошибкой — GPT не запускается, причина в `codex-log.txt`.

**Если результат не принят.** Сперва проверь задание: если виновата формулировка, исправь её и повтори с тем же исполнителем. Если виноват исполнитель: первый повтор — уровень выше, второй — следующая модель, дальше останови работу и сообщи пользователю. Каждый раз обновляй строку «Исполнитель».

## Цикл одной задачи

1. **Понять задачу.** Найди в `index.html` нужные места (Grep/Read), определи точно, что и где менять.
2. **Написать задание для GPT** в файл `TASK.md`:
   - номер пункта аудита (если есть) и цель одной фразой;
   - строка «Исполнитель» по роутеру;
   - какие функции/фрагменты менять (имена функций, характерные строки кода);
   - что именно должно получиться;
   - что НЕ трогать;
   - критерий готовности (как проверить).
   Одна задача — одно логическое изменение. Крупное разбивай на шаги.
3. **Запустить GPT:**
   ```
   codex exec -m gpt-6.1-sol -c model_reasoning_effort=medium -s workspace-write "Выполни задание из файла TASK.md. Соблюдай правила из AGENTS.md."
   ```
4. **Проверить результат:**
   - `git diff` — изменено только то, что в задании; нет переформатирования, лишних правок, удалённого кода;
   - логика соответствует правилам предметной области (ниже);
   - синтаксис JS не сломан (например, извлечь `<script>` и прогнать `node --check`);
   - при возможности открыть страницу и проверить сценарий из критерия готовности.
5. **Решение:**
   - всё верно → `git add -A` и `git commit -m "<пункт аудита>: <что сделано>"`;
   - есть ошибки → допиши в `TASK.md` раздел «Замечания» и запусти GPT снова;
   - GPT сломал файл → `git checkout -- index.html` и переформулируй задание.
6. **Отчёт пользователю:** какой пункт аудита выполнен, кто исполнял (модель / уровень), что изменилось, что проверено.

Не правь `index.html` сам, кроме мелочей в 1–2 строки, — правки делает GPT.

## Правила предметной области (решения пользователя)

- Трапезная — по сути домашняя кухня большой семьи: не привязана к СП/СанПиН, проектируем по здравому смыслу.
- Главное — приготовление: обязательно основное тепловое оборудование (пароконвектомат и/или индукционная плита); холод необязателен; планировка строится вокруг тепловой линии.
- Всегда рекомендуем индукцию, а не электроплиту.
- Доступная мощность на старте — не ограничение: мощность определяет технология, ввод можно увеличить.
- Газ — законный способ сэкономить электромощность; есть опция «Есть газ». Газовое оборудование можно ставить ~6 м от точки газа (2 м шланга — лишь упрощение).
- Шоковая заморозка — технологическое оборудование, не заменяет морозильник для хранения.
- Оборудование стоит вплотную к стене, без зазора сзади. Исключение: пароконвектомату нужно 50 мм от стен/выступов (сзади и сбоку у стены), не от соседнего оборудования.
- Глубину меняет только нейтральное оборудование (столы, стеллажи, шкафы, моечные ванны), округление вниз до 600/700/800; тепловое, холодильное и электромеханическое — по паспорту; холодильные шкафы стоят в конце линии и не задают её глубину.
- Электрощит (на уровне глаз): перед ним только нейтральное оборудование или холодильный стол до 950 мм; никакого теплового и моечного; источники воды не ближе 1 м.
- Слив от прибора до канализационного выпуска — не длиннее 5 м, вдоль стен; дверные проёмы для трубы непроходимы.

## Публикация и история версий

- Сайт для коллег: https://pro100po.github.io/refectory-app/ ; история версий: https://pro100po.github.io/refectory-app/versions.html
- После принятой правки (accept) наблюдатель сам делает коммит, кладёт копию `index.html` в `versions/`, обновляет `versions.html` и отправляет всё на GitHub (`git push origin main`). Делать это вручную не нужно.
- Первая строка `commit-msg.txt` попадает в историю версий как описание — пиши её понятно для коллег: «Пункт аудита 3: …».
- После accept сам не жди и не читай лог — отправь помощника на **Haiku** (Agent, model: haiku, run_in_background): цикл «фоновый `sleep 30` → `device_list_dir` → есть ли `done.flag`», максимум 6 циклов; когда `done.flag` появился — прочитать `git-log.txt` и ответить одной строкой: «опубликовано» или текст ошибки (строки с error / rejected / fatal). Если ошибка — сообщи пользователю.
- **Папку `versions/` и файл `versions.html` не читать, не искать в них и не менять** — это архив, лишнее чтение тратит лимиты. Поиск по коду — только в `index.html` (Grep с `path: index.html`).
- Откат к старой версии — только по просьбе пользователя: `git checkout <хеш> -- index.html`, затем обычный accept.

## Ожидание GPT (экономия лимитов)

Работа из чата идёт через наблюдатель `watch.ps1`: Claude кладёт `TASK.md` и `go.flag`, наблюдатель запускает GPT и по окончании создаёт `done.flag`.

1. После отправки задания поставь свой фоновый таймер (`sleep` с run_in_background) на минимальное ожидаемое время работы GPT: мелкая правка ~60 с, крупная 2–3 мин. Пока таймер идёт, не проверяй папку.
2. Затем НЕ проверяй сам — запусти фонового помощника на модели **Haiku** (Agent, model: haiku, run_in_background): цикл «фоновый `sleep 15` → дождаться уведомления → `device_list_dir` папки → есть ли `done.flag`», до появления `done.flag` или максимум 40 циклов (~10 мин). Ничего не читать и не менять, отчёт одной строкой.
3. Получив отчёт «done.flag есть» — переходи к проверке правок. Если лимит циклов исчерпан — посмотри `codex-log.txt` и сообщи пользователю.
Замер: проверка силами Opus ≈ 0,3% лимита сессии, силами Haiku — примерно в 20 раз дешевле.

## Работа из облачной сессии (мост через GitHub)

Облачная сессия не видит папку на компьютере, поэтому задания GPT идут через GitHub; `watch.ps1` раз в ~30 с проверяет ветки `claude/*`.

- В своей ветке облачный Claude кладёт:
  - `bridge/task.md` — задание (то же, что `TASK.md`, со строкой «Исполнитель»);
  - `bridge/commit.txt` — сообщение коммита для accept (первая строка — для истории версий);
  - `bridge/cmd.txt` — одна строка `<id> <команда>`, id каждый раз новый (например `20261103-1530`).
- Команды: `run` — новое задание (index.html сначала возвращается к последней принятой версии); `rerun` — повтор с замечаниями (правки GPT остаются); `accept` — принять (коммит в main, копия в `versions/`, публикация; папка `notes/` из ветки тоже попадает в main); `reject` — отклонить.
- Ответ наблюдателя — в той же ветке: `bridge/result/status.txt` (`<id> done|accepted|rejected|error-…`), рядом `index.html`, `review.diff`, `codex-log.txt` или `git-log.txt`.
- Облачный Claude ждёт ответа фоновым циклом `git fetch` + проверка `status.txt`, проверяет `bridge/result/index.html` против `origin/main:index.html`, затем шлёт accept/reject/rerun.
- Перед новой задачей облачная ветка перестраивается на свежий `origin/main` (сохраняя свои `notes/` и `bridge/`).
- Итоги проверок и планы заданий записывай в `notes/` — так локальная и облачная сессии продолжают работу без повторного анализа.
- Не работай одновременно из облака и с компьютера: у них одна рабочая папка наблюдателя.
