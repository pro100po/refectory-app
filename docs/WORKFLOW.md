# Работа над проектом

Пользователь общается с ведущим в чате. Ведущий показывает варианты, рекомендацию, цель и план, ожидаемый результат и проверки; после согласования ведёт шаги без повторных запросов на продолжение. Перед каждым шагом он кратко сообщает ожидаемый результат. Он выбирает исполнителя и проверяющего по общим договорённостям, проверяет ключевые доказательства и принимает результат.

## От задания до принятия

1. Перед работой ведущий проверяет состояние проекта, существующие изменения и процессы, затем готовит конкретное задание с границами файлов и критериями проверки. Роль и путь к файлу задания указываются явно при каждом запуске.
2. Каждый запуск имеет собственный идентификатор и каталог `.codex-runs/<id>/`: копию задания, состояние, события, вывод и отчёт. Копия задания не меняется. Одновременно допускается только один изменяющий CLI-исполнитель; независимые помощники чата могут читать и анализировать параллельно. Их стадии фиксируются ведущим явно, а не выдаются за автоматически полученные события.
3. Исполнитель работает в скрытом независимом процессе. `watch.bat` открывает отдельное окно состояния; закрытие окна не завершает исполнителя. Окно показывает фактические стадии и события, время, сохранение и публикацию без выдуманного процента или срока.
4. После завершения ведущий изучает отчёт и изменения, проверяет область файлов и критерии. Содержательная проверка привязана к фактическим изменениям: после изменения результата нужна новая проверка. Принятый промежуточный шаг сохраняется локальным коммитом только с проверенными файлами из разрешённого списка. Ошибка сохранения не означает, что шаг сохранён.
5. При отклонении изменения сохраняются для разбора; широкий сброс не выполняется. Исправление задания или повтор оформляют явно, не затирая чужие изменения. При прерывании сначала восстанавливают фактическое состояние, а не считают работу успешной.

## Публикация и состояние

На GitHub отправляют только полностью завершённый и принятый пункт. Перед отправкой проверяют ветку, удалённое состояние и состав всех ожидающих коммитов. Публикация проверяется отдельно от отправки: успешный push ещё не подтверждает развёртывание сайта. При изменении приложения создаётся запись истории и архив; инфраструктурное изменение само по себе не создаёт версию приложения. Существующие архивы сохраняются.

Основной актуальный статус проекта ведётся отдельно в `PROJECT_STATUS.md` ветки `project-status`, не переключая рабочую ветку и не включая посторонние файлы. Ссылка со страницы истории: https://github.com/pro100po/refectory-app/blob/project-status/PROJECT_STATUS.md. До создания ветки ссылка может быть недоступна. `notes/infrastructure-status.md` фиксирует переход инфраструктуры и не является вторым общим статусом проекта. В основном статусе фиксируют цель, выполненное, проверки, текущий и следующий шаг, решения, вопросы, дату и ссылки. Подробные технические события хранятся локально; секреты и журналы в публичное состояние не выгружаются.

Старые флаги Claude и опрос его веток не используются. Монитор не запускает работу и не публикует изменения при открытии.

## Команды для ведущего

Команды выполняются в PowerShell из папки проекта. `watch.ps1` без параметров показывает состояние; `watch.bat` открывает окно наблюдения. В примерах значения в угловых скобках заменяются реальными; список файлов передаётся как массив PowerShell. Эти команды выполняет ведущий, пользователю вводить их не требуется.

```powershell
./watch.ps1 -Command status
./watch.ps1 -Command monitor -Once
./watch.ps1 -Command run -TaskFile '<путь к заданию>' -Files @('index.html') -Model sol -Effort high
./watch.ps1 -Command rerun -Id '<id предыдущего запуска>' -TaskFile '<путь к новому заданию>' -Files @('index.html') -Model sol -Effort high
./watch.ps1 -Command manual -TaskFile '<путь к заданию>' -Files @('AGENTS.md', 'docs/WORKFLOW.md') -Baseline '<исходный commit>'
./watch.ps1 -Command review -Id '<id>' -Evidence '<файл проверок и решения>'
./watch.ps1 -Command accept-step -Id '<id>' -Message '<описание шага>'
./watch.ps1 -Command reject -Id '<id>'
./watch.ps1 -Command recover
./watch.ps1 -Command publish -CompleteItem -Message '<описание завершённого пункта>' -DeployTimeoutSeconds 300
./watch.ps1 -Command update-status -StatusFile '<путь к подготовленному PROJECT_STATUS.md>'
./watch.ps1 -Command record-stage -Stage '<этап>' -StageAction start -Model sol -Effort medium -Message '<детали>'
./watch.ps1 -Command record-stage -Stage '<этап>' -StageAction end -Model sol -Effort medium -Message '<результат>'
```

`run` требует явного задания и точных разрешённых файлов; модель и уровень указываются явно. `rerun` повторяет завершённый непринятый запуск с новым заданием, идентификатором и журналами, сохраняя прежние правки и копию старого задания; прежний запуск отмечается `superseded`. Прежние runner и CLI должны завершиться, ветка и исходный коммит — совпадать, подготовленных к коммиту файлов быть не должно. Фактические правки должны входить в оба списка разрешённых файлов; блокировка принадлежит прежнему запуску либо свободна после отклонения. `max` допускается только по прямой просьбе пользователя с `-AllowMax`; `ultra` не используется. `manual` регистрирует уже выполненную ручную работу с исходным коммитом, не изображая запуск CLI. `review` требует непустой файл с результатами проверки и решением; `accept-step` сохраняет проверенные изменения локально. Если проверенный результат не содержит изменений, `accept-step` завершает его со статусом `accepted-no-changes`, не создаёт коммит и освобождает блокировку. `reject` отмечает отклонение и освобождает блокировку, сохраняя изменения; `recover` предназначен для восстановления состояния прерванного процесса. `record-stage` вручную отмечает работу помощника чата.

`publish -CompleteItem` предназначен только для полностью завершённого пункта; отправка и развёртывание учитываются отдельно. `update-status` обновляет отдельную ветку из явно указанного файла. Параметр `-Repo` задаёт другую папку проекта при необходимости. `-TestMode`, `-TestCli` и `-TestSkipDeployment` предназначены только для изолированных проверок; пропуск проверки развёртывания не означает успешное развёртывание.

Если запуск скрытого процесса через Windows CIM запрещён средой инструментов, ведущему нужен разрешённый доступ к Windows-сессии; повышение модели и отключение ограничений Codex не устраняют эту причину.

После аварийного прерывания ведущий самостоятельно проверяет дерево процессов исполнителя: не остались ли работающие codex, node или оболочки именно этого запуска. Результат и способ проверки он записывает в отдельный файл. Для `reject` или `rerun` запуска со статусом `interrupted` обязателен параметр `-Evidence '<файл проверки процессов>'`; без него блокировка сохраняется. Подтверждение копируется в журнал запуска. `review` и `reject` также отказывают, пока записанные runner или CLI ещё работают. Автоматического завершения посторонних процессов нет; пользователь не обязан выполнять эти технические команды.
